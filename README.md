# bookmark-alpha

**把「从信息里找机会」这件事，挂成每天自动跑的定时任务。**

你只管刷 X，看到好东西顺手点个书签。第二天早上，昨天收藏的东西已经经过「采集 → 去重 → 统计 → DBS 商业闸门」；你拿到的是一张**可验证的机会候选**，或者一条明确的淘汰原因——**跟你手上的东西怎么接、第一步具体做什么、什么时候没信号就放弃**。

这是一个 Claude Code Skill，设计来当 routine 跑（Codex 之类支持定时任务的 agent App 同理）。

---

## 为什么是「每天」

两个原因：

**收藏是完成的错觉。**你点书签那一下，大脑已经把奖励发给你了，所以你再也不会打开它。收藏夹不是资料库，是墓地。

**机会有保质期。**一条书签的价值从你点下它那一刻开始衰减——窗口期的活动过期了，热的东西冷了，先发优势没了。攒一个月再回头翻，翻到的全是尸体。

所以这件事必须每天做。而每天都要做的事，只能交给机器。

---

## 它跟「AI 帮你总结收藏夹」有什么不同

总结类工具给你**更短的资讯**。资讯不改变任何事——你只是知道了更多东西。

这个 skill 的核心判断是：**EV 是相对的，收入证据不是推断出来的。**

> 「有人靠 Cursor 接单月入 3 万」——对一个会写代码、手上有闲置时间的人，这是一张可执行的机会卡；对一个不写代码的人，这是一条让他心痒然后什么也不会发生的娱乐信息。
>
> 信息本身没有 EV，信息 × 你手上的东西才有 EV。

所以它第一次运行会先问你手上有什么（技能、产品、流量、渠道、时间、能亏的钱、红线、正在做的事），建一份**资产档案**。之后每天的判断都拿这份档案当尺子；书签里的收入截图、粉丝数和他人战绩只算外部陈述，不算你的收入。

## 统计之后的 DBS 商业过滤

统计只回答「今天收到了什么」，不回答「什么能赚钱」。统计完成后，所有可能进入机会路由的书签必须再过一次 DBS 闸门。DBS 是一套商业判断协议，不是本项目必须安装的 npm 包；宿主有 `dbs-diagnosis` 时调用它，没有时按下面的内置清单执行，工具不可用也不能放宽标准。

### 先做三道低成本筛选

每条新书签依次过三道，任何一道不过就离开机会路由：

| 闸门 | 问什么 | 出局的是 |
|---|---|---|
| 一、机会还是消遣 | 这条指向一个具体动作，还是只指向一种情绪？ | 段子、纯观点、没有可复制机制的成功感言 |
| 二、接不接得上 | 执行它需要什么，你现在有几成？ | 缺渠道、缺资质、缺几个月技能积累的——**EV 归零** |
| 三、最小验证 | 能不能 3 天内、200 块以内、一个动作出真假信号？ | 说不出动作的，和「先学两个月再说」的 |

### 再过一次 DBS 五层商业闸门

对通过低成本筛选的条目，逐层记录证据，不允许从「别人说赚到」跳到「我能赚钱」：

| 层 | 必须回答 | 不通过时 |
|---|---|---|
| 语言 | 买家是谁、买什么、多少钱、交付什么？ | 没有明确对象和交付，标记 `needs_evidence` |
| 假设 | 哪个环节被默认成「有流量就会付款」或「做出来就有人要」？ | 写出被拆掉的假设，标记 `disqualified` |
| 逻辑 | 证据是在证明相关性，还是证明买家真的付过钱？ | 把幸存者故事降为 `reported`，不立机会卡 |
| 事实 | 案例、价格、规则和链接能否被独立核对？ | 证据不足，标记 `needs_evidence` |
| 信息 | 今天是否已有买家、报价、交付边界和一个验证动作？ | 不做 MVP，写清缺哪条信息 |

**通过 DBS 只代表「值得做一次商业验证」，不代表已经赚钱。** 一个真正的收入结论必须经过证据阶梯：

| 等级 | 证据 | 能说什么 |
|---|---|---|
| P0 | 想法、观点、截图、单条成功故事 | 仅作信号 |
| P1 | 明确买家、报价和交付边界 | 可形成待验证候选 |
| P2 | 真实线索、回复或明确询价 | 有需求信号，仍非收入 |
| P3 | 报价被接受并完成付款 | 有一笔付款证据 |
| P4 | 同类买家重复付款或复购 | 有重复收入证据 |

项目输出中只能把 P3/P4 写成付款/复购证据；P0-P2 一律使用「候选」「待验证」「外部陈述」等词。

**绝大多数看起来很赚钱的书签会在这组闸门里被降级或淘汰，那正是它该待的地方**——一个执行不了或没有买家证据的机会，跟一个不存在的机会，对你完全等价。

闸门出局的不会被扔掉，走旁路归档成三类：认知（必须写「能迁移到我正在做的哪件事」）、内容素材、以及你自己的注意力画像。**跑上三个月，最后那一栏会比机会卡更值钱——它是你的行为数据，别人拿不到，而且下一个读它的 agent 能靠它预判你想干嘛。**

每轮简报必须先报统计，再报 DBS 结果：

```text
抓取 N / 新增 A / 历史 B / 机会路由 C
DBS 送审 C → 可验证候选 D / 待补证据 E / 消解 F
证据等级：P0 x / P1 x / P2 x / P3 x / P4 x
```

## 还有一条反向机制

每轮都会回看存量机会卡。立了 3 轮没动作的点名，点名 2 次还没动作的**强制关闭并写下原因**。

> 堆积的机会卡不是资产，是另一种形式的收藏夹。一个不会关卡的机会队列，三个月后跟你的书签墓地长得一模一样。

## 安装

```bash
git clone https://github.com/lashimao/bookmark-alpha ~/.claude/skills/bookmark-alpha
```

**前置**：宿主提供一个已登录 X 的官方 Chrome 浏览器连接，能在 `https://x.com/i/bookmarks` 读取可见书签内容。项目本身不安装 DVS/DBS，不读取 cookie、localStorage、profile、ct0 或个人 bearer，也不依赖 X 的 GraphQL 私有请求；浏览器不可用时必须明确报告并停止，不得用历史数据冒充本轮结果。

### 第一步：手动跑一次

在 Claude Code 里说「扫书签」。它会问你四个问题建资产档案，然后跑第一轮。

**这一步必须手动做完**——定时任务模式下 skill 不会问问题，没有档案它只能瞎判。

### 第二步：挂成每天自动跑

建一个每天执行的定时任务，prompt 写：

```
调用 bookmark-alpha skill 跑今天这一轮。按无人值守模式执行：
先统计书签，再对可能赚钱的条目执行 DBS 商业过滤；不问问题、不做花钱/发布/碰凭证的动作，零候选就如实交白卷。
```

建议时间：**你醒之前**（比如早上 7 点）。起床时昨天的收藏已经判完了。

Codex 之类支持定时任务的 agent App 同理——把仓库放进它读得到的 skill 目录，建一条每日自动化，prompt 同上。只要那个 agent 能①读本地文件②驱动一个登录着 X 的浏览器，它就能跑。

纯 cron 也行：

```bash
0 7 * * * cd ~ && claude -p "调用 bookmark-alpha skill 跑今天这一轮，无人值守模式" >> ~/.bookmark-alpha/cron.log 2>&1
```

### 你每天会看到什么

```
抓取 20 / 新增 12 / 历史 8 / DBS 送审 4 → 候选 1 / 待补证据 2 / 消解 1
证据等级：P0 2 / P1 1 / P2 1 / P3 0 / P4 0

【可验证候选】
- 书签导出工具 → P1；先向 3 个明确买家发出同一报价，48 小时内看是否有回复或询价

【明确边界】
- 这不是已赚钱结论；没有付款证据就不写成收入

【存量提醒】
- 「虚拟资料店」卡立了 4 轮零动作，建议推进或关闭

【异常】无
```

**零机会卡是正常结果**，一轮 20 条书签里有 1 张能立卡就已经很好。硬凑机会卡是这个 skill 最容易变质的方式——所以它被明确要求宁可交白卷。

### 产出文件

全部在 `~/.bookmark-alpha/`，纯本地，不经过任何第三方服务：

```
assets.md          你的资产档案（判断基准）
opportunities.md   机会卡队列
notes.md           认知沉淀
content-ideas.md   内容素材
self-portrait.md   你的注意力画像
processed.md       去重台账
```

## 技术说明

书签采集由宿主的官方浏览器适配器完成，优先读取 X 页面可见 DOM，并返回统一字段：作者、状态链接、时间、正文和采集状态。采集器与 DBS 过滤器分离：采集器只负责事实输入，DBS 只负责商业判断，输出带证据等级和淘汰原因的本地台账。

本项目不把「能做出来」「有人发过战绩」「有流量」当作收入证明。浏览器连接、DBS skill 和任何外部模型不可用时都 fail closed：可以输出 `needs_evidence`，不能放行成机会候选。
